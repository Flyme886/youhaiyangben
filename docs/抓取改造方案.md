# 有害样本任务台 · 云服务器抓取改造方案（小程序版）

> 版本：v1.1（2026-10-30）
> 状态：待用户批准后实施
> 变更：**入口从飞书机器人全面切换为微信小程序「样本任务台」，飞书路线废弃**；抓取改造方案主体不变
> 前提约束：小程序是要交付的产品，**抓取与生成链路必须完全跑在云服务器上，禁止依赖本地 Mac（含 EgoLite/Ego Light 方案）**

---

## 一、我们要的结果（重述）

**业务用户在微信小程序「样本任务台」上传一份含有害内容链接的 Excel → 云服务器自动完成截图、质检、结构化判定 → 每 50 条生成一份 Word 文档 → 小程序内查看任务进度、下载/分享 Word 结果。**

- 小程序 ICP 备案已通过（2026-10），当前阶段：测试
- 云服务器（`/opt/harmful-sample-web`，FastAPI + 单 worker，端口 8787）已具备：任务队列、Excel 上传、Playwright/DrissionPage 截图、质检、Word 生成、压缩包导出——**工作流后端逻辑不变，只把入口和回传通道从飞书换成小程序**
- 交付的硬指标：云服务器端抓取成功率从实测 **1.5%** 提升到 **≥85%**，否则产出全是"截图待补"，不可交付

**明确排除的路**：
- ❌ 飞书机器人入口（废弃）
- ❌ Mac 本地跑抓取回传服务器（用户已否决，违反交付约束）
- ❌ 云服务器装 EgoLite（仅 macOS/Windows 客户端，Linux 未支持；浏览器本体闭源）
- ❌ 云服务器装 macOS（违反 Apple EULA，国内云厂商无 mac 实例）
- ⚠️ 云服务器装 Windows Server + EgoLite（技术可行但不解决 IP 问题，仅作备选）

## 二、整体架构（小程序版）

```
微信小程序「样本任务台」（miniprogram/）
   │  wx.login → code2session 静默登录（自定义 token）
   │  wx.uploadFile 上传 Excel（创建任务）
   │  轮询/下拉刷新任务状态
   ▼
FastAPI 后端（云服务器 8787，HTTPS + 已备案域名）
   │  任务队列（单 worker）→ Excel 预检/去重
   │  抓取层：Patchright + DrissionPage + 登录态 + ddddocr（本方案重点）
   │  质检层：三层降级判定（语义快照→截图→CDP）
   ▼
产物层：截图清单 + 样本级 JSON
   │  每 50 条生成 1 份 Word（备份：zip）
   ▼
回传：小程序任务详情页展示结果 → wx.downloadFile 下载 Word / 分享文件
```

### 小程序端需要配套的点（非抓取，但交付必查）

| # | 事项 | 说明 |
|---|---|---|
| S1 | **request/uploadFile/downloadFile 合法域名** | 全部指向已备案的 HTTPS 域名，在小程序后台配置；测试期可用"不校验合法域名"调试，提审前必须配齐 |
| S2 | **登录体系** | wx.login → 服务端 code2session 换 openid → 签发自定义 token；不收集多余用户信息 |
| S3 | **任务状态通知** | 第一版用任务列表轮询即可；体验优化后续接订阅消息（任务完成提醒，需用户订阅授权） |
| S4 | **用户隐私保护指引** | 小程序后台配置隐私协议；若涉及相册选文件/保存文件需对应授权弹窗 |
| S5 | **类目核查** | 确认小程序类目与"内容审核工具"定位匹配（工具类），提审前核对资质要求，以微信官方最新规则为准 |
| S6 | **文件大小限制** | wx.uploadFile 有大小限制，Excel 先按几十 KB~几 MB 量级设计，超限做前端校验提示（具体上限以官方文档核实） |

## 三、现状与差距

### 当前云服务器抓取配置

| 项 | 现状 |
|---|---|
| 服务 | FastAPI + 单 worker，端口 8787 |
| 主抓取引擎 | 裸 Playwright 无头（headless=true，desktop UA，整页截图） |
| 反爬分流 | 仅小红书、微博走 DrissionPage（`DRISSION_DOMAINS`） |
| 登录态 | `storage_state.json`，有效期 7 天，靠后台上传 |
| 验证码 | 阈值 20 条暂停，无自动识别 |
| 质检 | 截图空白/超时即判 blocked_or_blank，误判率高 |

### 历史实测差距（200 条 URL）

| 状态 | 占比 | 目标 |
|---|---|---|
| 成功 ok | 1.5% | ≥85% |
| blocked_or_blank | 64% | <15% |
| login_required | 28.5% | <5% |
| captcha_detected | 5.5% | 自动处理或人工兜底 |

### 失败根因（四层全裸）

1. 裸 Playwright 无头 → 自动化特征全暴露（协议层/属性层/环境层）
2. 数据中心 IP → 信誉分极低，风控先看 IP 再看指纹
3. 登录态缺失/过期 → 28.5% 直接卡死
4. 验证码无处理 → 撞到即失败

## 四、抓取改造方案（分层，EgoLite 思想融入）

> EgoLite 调研结论：其 ego-browser skill 层为 MIT 开源，可自由借鉴思想。
> 借鉴三点：①Task Space 隔离 + 登录态继承 ②三层降级质检 ③Site Learnings 站点经验沉淀。

### 第一层：低改动高收益（先行落地）

| # | 改造项 | 具体做法 | 预期 |
|---|---|---|---|
| 1.1 | **Patchright 替换裸 Playwright** | 补丁版 Playwright，drop-in 改 import，关闭 CDP 协议层泄漏；现有 `capture_links.py` 链路基本不动 | 消除自动化特征，blocked 大幅下降 |
| 1.2 | **登录态工业化** | 每平台一份 `storage_state.json`（抖音/小红书/微博/百度）；后台上传 + 过期提醒机制（7 天有效期） | login_required 28.5% → <5% |
| 1.3 | **ddddocr 验证码自动识别** | 接入 sml2h3/ddddocr（MIT，离线，CPU 100ms），图形码自动填、滑块缺口 slide_match 自动拖 | captcha 不再直接失败 |
| 1.4 | **Task Space 隔离**（借鉴 EgoLite） | 每任务独立 browser context + 独立登录态，任务间 cookie 互不污染，支持并行 | 多任务并行且稳定 |

### 第二层：真实浏览器环境（第一层实测不够再上）

| # | 改造项 | 具体做法 | 预期 |
|---|---|---|---|
| 2.1 | **Xvfb + 有头真实 Chrome** | Linux 装 Xvfb 虚拟显示，跑有头 Chrome（对平台=真实桌面用户），Playwright/DrissionPage 连接之 | 等价复刻 EgoLite"真实指纹" |
| 2.2 | **DrissionPage 全面接管** | `DRISSION_DOMAINS` 扩展至抖音等全平台；listen 模式监听接口直接拿 JSON（借鉴 EgoLite CDP 事件监听） | 比解析 DOM 稳 |
| 2.3 | **动作拟人化** | 请求间隔 ±30% 随机抖动、随机滚动、禁止固定轮询 | 降低行为序列检测命中 |
| 2.4 | **三层降级质检**（借鉴 EgoLite） | 语义快照（正文是否真的渲染）→ 截图视觉 → CDP 底层探查，替代纯截图空白判定 | blocked 误判显著下降 |
| 2.5 | **Site Learnings 站点经验沉淀**（借鉴 EgoLite） | 每平台域名一份抓取配置（等待时长/滚动策略/选择器/登录态要求），失败重试自动复用成功经验 | 失败任务越跑越准 |

### 第三层：兜底（大概率用不上）

- Camoufox（引擎级指纹改造的 Firefox）兜底难缠域名
- 国内住宅代理池（数据中心 IP 信誉是所有方案的共同天花板；若前两层做完 blocked 仍高，即是 IP 问题）
- 备选架构：加一台 2C4G Windows 轻量云专跑 EgoLite 抓取、回传 Linux 主服务器（仅当前两层全面失败时考虑）

## 五、验收标准

用同一份 200 条测试 Excel 做改造前后对比：

| 指标 | 改造前 | 第一层后 | 第二层后 |
|---|---|---|---|
| 整体成功率 | 1.5% | ≥50% | ≥85% |
| blocked_or_blank | 64% | <35% | <15% |
| login_required | 28.5% | <5% | <5% |
| captcha 自动处理率 | 0% | ≥60% | ≥90% |

抓取达标 → 进入整链路联测：**小程序上传 Excel → 任务创建/状态流转 → 抓取产出 → Word 生成 → 小程序内下载/分享**，按第二节 S1~S6 逐项核对后提审。

## 六、实施顺序（建议）

1. 第 1 步：后端完成 Patchright 替换 + 登录态机制 + Task Space 隔离（1.1/1.2/1.4）
2. 第 2 步：接入 ddddocr（1.3）
3. 第 3 步：准备各平台账号 → 云服务器生成/上传各平台登录态
4. 第 4 步：小批量实测（10~20 条覆盖各平台）→ 200 条全量对比，对照验收表
5. 第 5 步：视结果决定是否进入第二层（Xvfb + 真实 Chrome + DrissionPage 全接管）
6. 第 6 步：抓取达标后，小程序端 ↔ 后端整链路联测（S1 域名、S2 登录、S3 状态、S4~S6 合规）
7. 第 7 步：提审前检查（类目/隐私/域名配置）→ 提审发布

## 七、风险与合规提示

- **小程序侧**：工具类类目与资质、用户隐私保护指引、合法域名配置，均以微信官方最新规则为准；提审前逐项核对
- **采集侧**：仅限公开内容、控制频率、用于内容审核场景；交付前过一遍平台条款与法务口径
- **账号风险**：登录态绑定的平台账号可能被风控，建议使用专用采集号，与核心账号隔离

## 八、已落地 / 未落地（2026-11-03 校准）

> 本节是唯一可信的进度口径。上面第三～六节保留为最初的方案设想，
> 其中不少内容在 10-12 / 10-14 已随服务器改动实现，但当时没有回灌仓库。

### 已落地（代码在仓库里，可直接生效）

| 能力 | 位置 | 默认值 / 开关 |
|---|---|---|
| 住宅代理 | `capture_playwright.py` 读 `CAPTURE_PROXY` | 不填即直连 |
| 抓取并发（页面级） | `CAPTURE_BATCH_SIZE` | 3 |
| 批次随机间隔 | `CAPTURE_BATCH_DELAY_MIN_MS` / `MAX_MS` | 1200 ~ 3000ms |
| desktop UA 覆写 | `CAPTURE_USER_AGENT` | 空则用内置 Mac Chrome UA |
| locale / 时区 / Accept-Language | 代码内固定 | zh-CN / Asia/Shanghai |
| 容器内启动参数 | `CHROMIUM_ARGS` | 如 `--no-sandbox` |
| 任务并发（任务级） | `TASK_WORKERS` | 2 |
| SQLite 并发写 | `app/db.py` | WAL + busy_timeout 15s |
| 命中验证码仍出 Word | `app/task_runner.py` | 交付优先，不再 `paused_captcha` 中断 |
| 断点续抓 | `--previous-manifest` | 复用 status=ok 的记录 |

代理凭据**只经环境变量**传递，不进 argv、不进 `run.log`（`ps aux` 也看不到）。

### 已知但未验证的假设

「换住宅 IP 就能把成功率从 0 拉到 60%+」目前**没有实测数据**。
已验证的只有反证：无头 vs 有头 A/B 两组均 3/3 全验证码、并发降到 3 仍全验证码。
上线前必须先用 10 条真实链接做「直连 vs 代理」对照，再决定放量。
- **维护风险**：平台反爬持续升级，抓取层需定期维护；Site Learnings 机制可降低维护成本
