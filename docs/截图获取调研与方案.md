# 截图获取：调研结论与落地方案

> 版本：v2.0（2026-11-10）
> 取代：`docs/抓取改造方案.md` v1.1 的第四、五节（架构与约束不变）
> 约束不变：交付物必须是页面截图；抓取与生成全部跑在云服务器；不依赖任何人的本地电脑

---

## 一句话结论

**1.5% 主要不是「隐身不够」，而是服务器链路落后于本地已经验证过的经验。**
先把本地 `douyin-harmful-sample` 技能里的平台规则搬上服务器、把并发降回单线程、把判定改成特征表，
这一步不花钱、不换引擎，就能把头条 / 微博 / 贴吧 / 百度 / B 站这类「本来就能开」的平台拉起来。
之后再按平台逐个上真实浏览器、持久 profile、国内住宅出口，只在抖音和小红书上花钱。

---

## 一、先看清 1.5% 是怎么来的

`TASK_FAILURE_ANALYSIS.md` 的 200 条样本里，失败的不全是抖音、小红书，还有大量头条、视频号、微博、百度 mbd 链接。
对照代码，至少四类失败是**我们自己造成的**，与平台风控无关：

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| A | 微博用桌面版地址导航，必撞登录墙 | `capture_playwright.py` 无地址归一化 | 微博几乎全部 `login_required` |
| B | 「正文少于 20 字 → blocked_or_blank」 | `capture_playwright.py` 第 98 行 | 流式页面（抖音 / B 站 / 小红书）在 `load` 前截图就被判空；已删除页也被判失败 |
| C | 已删除 / 不存在页被当成失败 | 同上，无「deleted」状态 | 「该微博不存在」「帖子可能已被删除」本是有效证据，却被丢掉 |
| D | 并发：2 个任务 worker × 单任务 3 路（提交 a2db6d9） | `task_runner.py` / `.env` `CAPTURE_BATCH_SIZE=3` | 本地技能实测「并发立刻换来成簇验证码，还连累整个 IP 限流」 |

本地技能（Ego Lite + 真实浏览器 + 单线程）里已经写好了各平台的导航地址、特征表判定和节奏规则，但服务器的 `skills/harmful_sample` 链一条都没用上。
所以第一步不是换隐身引擎，而是**对齐**。

另有两类在网页上**根本取不到**，再强的浏览器也没用，要在产品层处理：

- **视频号**（`channels.weixin.qq.com/...`）：只能在微信客户端内打开，网页端只是跳转壳。
- **小红书无 token 链接**：监测表导出的 `discovery/item/{id}` 不带 `xsec_token`，直接打开一律 404 或回落首页。
  社区多处报告确认，token 由服务端下发，和账号、日期、来源都有关，不能从笔记 ID 推出来。
  唯一的补救办法是：在登录态下用站内搜索拿到带 token 的链接。
  （见 XHS-Downloader #186、MediaCrawler #510）

## 二、外部调研要点

**1. Patchright 的收益比预期小。**
2026 年有一份公开基准，测了 7 种工具 × 31 个反爬站点、共 651 次判定。结果如下：
- Patchright 只比原生 Playwright 多过 1 个站点（25 对 24）。作者认为，这 1 个的差异主要来自改用系统 Chrome（`channel=chrome`），而不是补丁本身。
- 唯一零拦截的是 nodriver。它不经过 Playwright/WebDriver 层，直接用 CDP 驱动系统 Chrome。
- 作者的判断是：自动化协议层的指纹比浏览器补丁更关键。

旧方案把 Patchright 列为第一层主力，预期偏乐观。

**2. 有头比无头明显更好。**
同一基准引用的另一组数据：同一款隐身浏览器在有头模式下通过率是 83.3%，无头模式只有 50%。
本地技能也独立得出同样结论：真实浏览器加持久 profile，比无头方案好得多。

**3. 只加代理不解决问题。**
基准作者还观察到一点：Linux 服务器挂住宅代理的表现，反而不如不挂代理的 Mac。
原因是 TLS、HTTP/2 和浏览器指纹仍会暴露宿主环境。
所以 IP 是天花板，但前提是浏览器环境先做对，代理才有意义。

**4. 小红书「没登录」是误判。**
Diana 项目的 PR #686 里有实测：未登录的普通浏览器能看到完整笔记。
直接请求 HTML 拿不到正文，是因为小红书已不再服务端渲染，笔记数据要等页面脚本跑完才出现。
所以小红书需要的是「渲染完再判定」，以及前面说的 token，而不是登录态。

**5. 验证码不破解。**
旧方案 1.3 计划接 ddddocr，自动识别图形码、自动拖滑块。这次建议**删掉这一项**：
- 本地技能已把「不破解验证码」定为授权边界；
- 自动破解平台安全验证有明确的合规和法律风险；
- 而且治标不治本，验证码是风控已经命中的结果。

撞到验证码后的做法：冷却 60–90 秒，重新导航一次；还不行就留白，并在交付说明里写清楚。

## 三、方案：四层，逐层验收

### 第 0 层：对齐本地经验（1–2 天，零成本，先做）

| # | 改动 | 做法 |
|---|---|---|
| 0.1 | **平台识别 + 导航地址归一化** | 把 `make_manifest_generic.py` 的 `platform_of` / `nav_url` 移到服务器链。具体规则：<br>• 微博 → `m.weibo.cn/detail/{bid}`<br>• 抖音 `/share/video/{id}` → `douyin.com/video/{id}`<br>• 小红书 → `explore/{id}?xsec_token=`<br>文档里写的始终是原表链接，只改导航地址。 |
| 0.2 | **特征表判定取代字数判定** | 按顺序匹配 `CAPTCHA_RE` / `DELETED_RE` / `LOGIN_RE`，均不命中且正文 < 20 字才判 `blocked_or_blank`。新增 `deleted` 状态，且**附图**（有效证据）。 |
| 0.3 | **等待策略** | `waitUntil: domcontentloaded` 加平台级 settle（抖音 3.5s、小红书 3.2s、微博 2.2s……沿用本地表），再滚动一屏触发懒加载。 |
| 0.4 | **并发降级** | `TASK_WORKERS=1`、`CAPTURE_BATCH_SIZE=1`，条间间隔 2–5s 随机。同平台连续请求之间额外加抖动。 |
| 0.5 | **同址去重** | 按归一化地址只截一次图，多条样本复用（转发号很多时收益明显）。 |
| 0.6 | **每 10–12 条重建标签页** | 渲染进程长跑会从 2 秒劣化到几分钟，这是本地实测。 |
| 0.7 | **探测步** | 正式抓取前每个平台先抓 1 条，30 秒内产出可达性表并写进 summary。小程序详情页可以直接展示「哪个平台打不开」。 |
| 0.8 | **按平台出统计** | summary 增加 `platform_status_counts`（平台 × 状态）。没有平台维度，就无法判断下一层该往哪里投入。 |

验收：同一份 200 条测试表重跑，产出「平台 × 状态」矩阵。预期非抖音、非小红书平台的成功率大幅回升。

### 第 1 层：换成「真实浏览器形态」（3–5 天）

| # | 改动 | 做法 |
|---|---|---|
| 1.1 | **Xvfb + 有头系统 Chrome** | 服务器装 `google-chrome-stable` 和 Xvfb，用有头模式运行，不再用 Playwright 自带的 Chromium。 |
| 1.2 | **改用直连 CDP 的驱动** | 主引擎换成 DrissionPage（仓库已有 `capture_drission.py`，`DRISSION_DOMAINS` 扩到全平台），nodriver 作为备选。Playwright 只留作兜底。 |
| 1.3 | **每平台一个持久 profile 目录** | 用 `--user-data-dir=/opt/.../profiles/{platform}` 替代 `storage_state.json`。cookie、localStorage、IndexedDB、缓存全部持久化，形态接近 Ego Lite。管理员在后台用「远程桌面（noVNC）」登录一次，后面就一直复用。 |
| 1.4 | **小红书 token 回收** | 对缺 token 的链接，先在登录态下站内搜索「标题前 N 字 / 作者」，从结果卡片 href 回收 token。搜不到就标 `need_token`，在交付说明里写明原因，不计入失败。 |

验收：抖音、小红书单独出成功率。如果 blocked 仍占主导，就是 IP 问题，进入第 2 层。

### 第 2 层：出口 IP（按需，产生持续成本）

- 只给抖音、小红书两个平台挂**国内住宅 / ISP 静态代理**，其他平台继续直连，控制成本。
- 静态 ISP IP 优于轮换住宅 IP：持久 profile 需要稳定的 IP 才能积累信誉，频繁换 IP 反而像异常登录。
- 需要采购合规的代理服务（实名、可开票、明确用途），这一项需要业务方拍板。

### 第 3 层：网页端取不到的部分（产品决策）

| 类型 | 建议 |
|---|---|
| 视频号链接 | 在探测步直接标 `platform_unreachable`，不消耗重试；交付说明写「视频号仅能在微信内查看」。 |
| 无 token 且搜不回的小红书 | 同上，标 `need_token`。 |
| 手机补图（**需决策**） | 在小程序详情页列出缺图条目，用户点开、复制链接、在手机 App 里截图后上传，服务器替换进 Word 并重出。抓取仍全部在服务器，人工只做最后一公里。这与「不依赖人工介入」的初衷有张力，请业务方决定是否开放。 |
| 云手机（redroid）跑 App 截图 | 风控姿态最强，但成本和运维最重（内核模块、ARM 适配、App 账号与协议风险）。只在前面各层全部失败时考虑。 |

## 四、验收口径（替代单一 85%）

用同一份 200 条测试表，按平台出矩阵，分层验收：

| 平台组 | 第 0 层后 | 第 1 层后 | 第 2 层后 |
|---|---|---|---|
| 头条 / 微博 / 贴吧 / 百度 / B 站 / 其它 | ≥ 70% | ≥ 85% | — |
| 抖音 | 记录基线 | ≥ 50% | ≥ 80% |
| 小红书（有 token 的） | 记录基线 | ≥ 60% | ≥ 80% |
| 视频号 / 无 token 小红书 | 正确归类为不可达 | — | — |

`deleted` 计入成功（附图）；`platform_unreachable` / `need_token` 单列，不计入分母。

---

## 五、建议的实施顺序

1. 第 0 层的 0.4（并发降级）：改 `.env` 即可，今天就能做。
2. 第 0 层其余项，同时加平台统计。
3. 重跑 200 条，看矩阵，再决定第 1 层要投入多少。
4. 第 1 层。
5. 视抖音 / 小红书的数字，决定是否采购第 2 层代理。
